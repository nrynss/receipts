# T2.3 answer and appeal handoff

The owner control API requires a caller-generated stable `action_key` for each answer and review action. Retries must reuse the key and the same payload; a distinct answer to the same stamp conflicts. Admit, context changed and appeal mutations recheck the connected owner, live session, current stamp and receipt eligibility in the ledger transaction. Moderator chat commands accept roles and identity only from the trusted Twitch adapter. `!receipts off/on` pauses stamps without stopping the runtime or audio. `!void <receipt-id>` removes the claim from public reads.

Only one appeal can be open per channel. The first vote from each trusted Twitch user is final; duplicate deliveries with the same choice are idempotent. The opening instant is inclusive and the deadline is exclusive. A tie or no votes records an inconclusive verdict. Invalid or expired appeals are cancelled without a verdict. Public snapshots include only counts and deadlines. Status events request an authoritative snapshot rebase, including after void or closure.

Startup must call `Store.RecoverDueAppeals` before serving requests; it closes overdue appeals without asserting live status or publishing a stamp. Every verified runtime activation must call `appeal.Service.StartChannel` before dispatching chat, to recover and schedule that channel's pending deadline. The runtime integration must pass the same Store and Manager instances as hosted controls. No live Twitch or model calls are used by these checks.

The recorded vote fixture is replayed twice through the service and ledger. Hosted HTTP tests cover owner and device authorization, idempotent answers, trusted voting, public projection, moderator pause/resume and void, and runtime restart recovery. Store tests cover concurrent clicks and votes, boundary times, ties, no votes, expired cancellation and startup recovery without a runtime. Full lore/demo acceptance remains T2.4; actual Twitch adapter activation and live verification remain P4.
