# Decisions API evaluation

## Recommendation

Receipts now uses GPT-6 Luna for production promise extraction and the Decisions API for sensitivity and contradiction classification. OpenAI's official deprecations page announces the removal of `gpt-4o-mini-2024-07-18` and recommends `gpt-6-luna`. Standard short-context pricing is $0.10/$0.50 per million input/output tokens for Luna, compared with $0.15/$0.60 for GPT-4o mini. Decisions uses $0.10 per million uncached input tokens and charges no output tokens. This makes Luna cheaper for structured generation, and Decisions especially cheap for classifications, but cost does not establish accuracy or safer routing.

The Decisions adapters are connected to the production intelligence path behind the existing extraction, sensitivity, and judge interfaces. Keep contradiction outcomes routed to review; no score threshold is active and automatic stamps remain disabled. Do not treat the API's confidence as calibrated probability. The current model assignments, input limits, spend reservations, and evidence caveats are documented in [production model path](model-migration.md).

The official API currently accepts `POST /v1/decisions` with `gpt-6-luna`. Choice answers include the chosen value, a probability for each supplied choice, and `confidence`. Predicate answers return a probability, while score answers are intended for ordered levels. `choice` is the direct fit for both three-way classification tasks. A refusal is a distinct answer type and must map to review for judging or fail closed for sensitivity. Cache writes, regional processing, and long-context multipliers can change the cost. GPT-6 Luna also supports Chat Completions and Structured Outputs, so the extraction schema can be retained while changing the model after offline and live compatibility checks. See [Decisions guide](https://developers.openai.com/api/docs/guides/decisions), [create-decision reference](https://developers.openai.com/api/reference/resources/decisions/methods/create), [GPT-6 Luna model details](https://developers.openai.com/api/docs/models/gpt-6-luna), [Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs), [pricing](https://developers.openai.com/api/docs/pricing), and [model deprecations](https://developers.openai.com/api/docs/deprecations).

## Evidence and limits

The post-collection owner audit reviewed the exact 44-item synthetic corpus and recorded six label corrections in an overlay. Original text, splits, model recordings, and the `review-only-v1` freeze remain unchanged. This is a post-collection audit, not a fresh prospective held-out experiment. It supports scoring the already-recorded run against the corrected labels, but it cannot establish an unbiased comparison for a new model or policy.

The corrected-label report still has zero automatic stamps in both partitions. That yields no precision estimate (`precision` is undefined), and recall is zero under the current review-only policy. It does not show that a confidence threshold would help. The small synthetic examples also cannot establish real-stream attribution, sensitivity, timing, or generalization. Preserve hard sensitivity and attribution gates outside the model; do not let a high score override them.

Decisions' `confidence` and option probabilities are model outputs, not evidence of calibration. Use them as ranking signals only. If a candidate auto-stamp threshold is explored, select it using development examples only, state the false-positive and abstention tradeoff, then freeze that threshold before looking at held-out results. Because these labels were reviewed after collection, held-out scores remain exploratory even when the policy is frozen. A fresh, prospectively labeled corpus is needed for a valid held-out claim.

## Bounded comparison plan

1. `TestCollectDecisionsComparison` compared legacy and Decisions sensitivity classifications on the same claim and later line, with labels withheld. It sent both texts to both sensitivity classifiers. If either sensitivity adapter flagged either text, neither judge received the pair; otherwise it compared the legacy judge and Decisions judge on identical inputs. It reused original text and did not repeat extraction or embeddings. Extraction compatibility was checked offline against the existing strict schema; no paid extraction comparison was part of this run.
2. Before each paid attempt, atomically persist a mode-0600 checkpoint containing the fixed dataset and source hashes, case ID, request digest, model, endpoint, policy, reserved spend, and pending state. Persist measured usage immediately after the response, then the sanitized answer and completion state. Never store provider bodies or credentials. A pending, unmeasured, or response-missing attempt stops the run and requires reconciliation; it must not be retried automatically.
3. The approved 34-case dev run completed with every attempt measured and no pending event. Actual charge was $0.00337445. The checkpoint reserved $1.00 total; the per-case ceiling was $0.078. No held-out collection was part of the approval.
4. Development scoring compared three-class judge outcomes, choice probabilities, confidence thresholds, abstention, false stamps, spend, and end-to-end latency. Sensitivity suppression rates are reported, but sensitivity false-positive/negative rates cannot be computed because the corpus contains no independent per-text sensitivity labels. Do not tune on held-out examples.
5. Freeze the adapters and any chosen threshold against the exact development report and source hashes. Only then may the ten held-out cases be run under a separately approved ceiling. Report the result as exploratory because label review followed the original collection.

The Decisions guide claims roughly 10x lower latency than Responses, but that is not a Receipts measurement. Measure end-to-end request latency in the comparison. For short-context standard Chat Completions, the current meter should charge Luna at 100 nano-USD/input-token and 500 nano-USD/output-token, versus 150 and 600 for GPT-4o mini. For Decisions, charge 100 nano-USD/input-token and zero for output. Obtain actual token usage from each response rather than estimating it from text size. Existing T5.4 spends include many pipeline calls and are not a like-for-like model comparison.

## Integration shape

The standalone adapters are wired behind the existing extraction, sensitivity, and judge interfaces. They validate the named answer, allowed choice, probabilities, source IDs, and measured usage; refusals and malformed output fail closed. Retain historical T5.4 source snapshots, model identifiers, and recordings for replay; new experiments use distinct model/source manifests. The production policy remains review-only.

The checkpointed collector reuses the atomic mode-0600 checkpoint, metering observer, request digest transport, and resume refusal for unresolved attempts. The completed dev run contains sanitized provider outputs only; no provider bodies or credentials are recorded. No held-out or additional live calls were made as part of the production model migration.

## Offline scorer and extraction compatibility

`cmd/receipts-eval-decisions` scores a completed comparison checkpoint against the owner-reviewed overlay while hashing and preserving the original corpus. On development data, it prints all 49 combinations for confidence and selected-choice probability thresholds (0.0 and 0.5 through 1.0 in 0.1 steps). Supply a threshold explicitly after inspecting the sweep to emit false-stamp IDs and text inspections and, optionally, a mode-0600 freeze bound to the exact development report, checkpoint, overlay, source hashes, and model map. A held-out invocation requires those exact dev artifacts and applies only that frozen threshold; it emits no held-out sweep. The command reports raw precision, recall, false-stamp and abstention rates. It does not choose a threshold or claim that API confidence is calibrated.

The six corrected labels are loaded only as a scoring overlay. Original labels, split assignments, input text, and recordings remain unchanged. The fixture is a post-collection audit, so even the held-out score is exploratory and cannot support a prospective accuracy claim. The report's false-positive list is intended for human inspection, especially for timing, attribution, and sensitivity errors. These checks remain independent product gates. Automatic stamps remain disabled.

Claim extraction uses `gpt-6-luna` with the existing strict JSON schema and usage meter. Production settings reject the retired GPT-4o mini snapshot for extraction or judging while historical evaluation adapters retain their fixed model identifier. Transcription and embeddings are outside this migration.
