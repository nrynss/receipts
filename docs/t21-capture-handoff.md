# T2.1 receipt capture handoff

`commands.Service` is the application decision path for `!receipt`. Callers pass an explicit trusted `commands.Authority` containing the active channel and session. Incoming chat channel/session fields are ignored; the broadcaster's trusted chat adapter supplies the Twitch user ID and login used for credit.

The extractor receives only broadcaster-attributed transcript segments in the configured lookback before the chat event's trusted receive time, mapped against the persisted session start. Future chat timestamps, chat events older than 30 seconds, future transcript offsets and sources outside the bounded window are rejected. The recorded/production response must cite one or more source segment IDs. Capture rejects citations outside that bounded set; the store then rechecks live session ownership, original command session, freshness, lookback and exact source text/offset/attribution in the same transaction as receipt and evidence insertion. Sensitive classification is required and runs over both the normalized claim and every original cited transcript segment; errors fail closed. Missing speech, extraction failure, sensitivity and duplicate/throttled commands have separate result codes for safe adapter replies.

Migration `004_capture.sql` persists command IDs and original session IDs per channel, admitted-attempt throttles, viewer credit and independent clip jobs. Throttles use server time and count every admitted attempt, including no-claim, suppressed and unavailable outcomes; rejected throttled arrivals do not extend the window. A command is claimed before transcript lookup/extraction, so redelivery cannot multiply work; an interrupted `processing` command stays deduplicated across restart. The receipt transaction creates a pending clip job separately from the text receipt. Clip dispatch failure leaves that pending job and cannot roll back the captured claim. Clip result updates are scoped to the channel and originating command ID; identical retries are safe and conflicting results fail.

`testdata/replay/t21-capture.json` runs the same service through `replay.Fixture.Run`, using the recorded extraction response in the service test. No provider or model is called by the offline fixture.

The service is not yet mounted in the production chat/runtime composition. TA.2 must pass its validated channel/session authority to this service and keep EventSub identity metadata trusted; P5 supplies the live extractor and sensitive-topic classifier. The throttle policy is one admitted request per viewer per channel in 30 seconds and at most three admitted channel requests in any five-second window.
